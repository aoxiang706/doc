# SSF-003 / SSF-005 / SSF-007 视频实时性测试方案

## 1. 三条需求的理解与职责划分


| 条目          | 需求摘要                                   | 你的理解                                      | 备注                                               |
| ----------- | -------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| **SSF-003** | 内部图像数据传输实时性：帧率≥30FPS，最大延迟≤10ms         | 测「解码得到图片 → 编码成视频前」这段时间                    | 嵌入式负责「解码→共享内存→交给 AI 前」的耗时；AI 内部处理时间由 AI 同事在算法侧打点 |
| **SSF-005** | 获取视频流实时性：帧率≥30FPS，最大延迟≤200ms           | C2 侧「点击播放→首帧出现」的耗时                        | 无现成量化数据，只能多次测试取平均；200ms 较严苛，1s 内出画可作为内部期望        |
| **SSF-007** | 域控给 C2/私有天盾的视频流实时性：帧率≥30FPS，最大延迟≤500ms | 在视频上叠加时间，对比「源端时间」与「C2 从 mediaMTX 拉流看到的时间」 | 你的方法（时间叠加 + 时间差）是业界常用做法，下面会结合现有代码和工具展开           |

## 2. SSF-003：内部图像数据延迟（解码→编码前，≤10ms）

**嵌入式可测段落：解码得到图像 → 通过共享内存交给 AI 之前**

- **建议打点**（在 [ros_ws/src/ptz_service/src/ptzDevice/ptzDeviceHepu.cpp](ros_ws/src/ptz_service/src/ptzDevice/ptzDeviceHepu.cpp) 及解码/送帧路径）：
  - T1：解码输出一帧图像的时刻（或从 Gst 回调拿到帧的时刻）
  - T2：该帧写入共享内存并通知 AI 之前的时刻
- **嵌入式可报的指标**：`T2 - T1`（即「解码→交给 AI 前」），满足 ≤10ms 的约束中属于嵌入式的一段。
- **AI 侧**：在 [ros_ws/src/ptz100_ai/perception/utils/visualization.cpp](ros_ws/src/ptz100_ai/perception/utils/visualization.cpp) 已有「AI delay」等（`Utils::skyfend_get_systimestamp() - inputs.timestamp`），可在此基础上拆出「从拿到帧到算法输出」的纯 AI 处理时间，与嵌入式段叠加即可得到「解码→编码前」总延迟。

**结论**：嵌入式测「解码→共享内存→给 AI 前」；AI 测「拿到帧→算法完成」；两者相加即为 SSF-003 所关心的内部图像链路延迟，可与 10ms 对比。

## 3. SSF-005：获取视频流实时性（C2 点击播放→首帧，≤200ms）

- **现状**：没有协议层或播放器层的现成「首帧时间」指标，只能通过操作侧统计。
- **推荐测试方式**：
  - **人工/半自动**：在 C2 多次「点击播放」，用秒表或高帧率录屏记录「点击→首帧出现」时间，取平均/百分位（如 P50、P95）。
  - **可选自动化**：若 C2 前端可插桩，在「请求播放」时记 T_start，在「首帧渲染/onFirstFrame」回调记 T_end，则 `T_end - T_start` 即单次首帧延迟，可上报或打日志做统计。
- **与 200ms 的关系**：200ms 作为规范值可保留；内部可同时统计「1s 内出画」比例作为体验指标，便于和产品/需求方沟通。

**结论**：以多次测试取平均/百分位为主；若有 C2 端首帧回调，可做自动化采集，无专门「视频流延迟可视化工具」也可完成 SSF-005 评估。

## 4. SSF-007：域控→C2 视频流实时性（≤500ms）— 时间叠加 + 工具

### 4.1 你提到的方法（在视频中叠加时间再对比）

这是**常用且正确**的端到端延迟测量方式：

- 在**源端（AGX/域控）**在编码前给每一帧叠加「该帧对应的源端时间」（建议到毫秒，如 `YYYY-MM-DD HH:MM:SS.mmm`）。
- C2 从 mediaMTX 拉流播放时，观众看到的是「画面里的时间」。
- **端到端延迟** ≈ 观众当前设备时间 − 画面上显示的时间（若 AGX 与 C2 已做时间同步，如 NTP）。

**本仓库已有可复用实现**：

- [public/gstNvDeeps/examples/videoRtspMtxTest.cpp](public/gstNvDeeps/examples/videoRtspMtxTest.cpp) 中已有「加时间显示，测试延迟」：在解码回调里用 `std::chrono::system_clock::now()` 生成时间字符串，`cv::putText` 画到帧上再推流到 mediaMTX。  
- 若实际推流到 mediaMTX 的路径与 PTZ 服务一致，可在**同一位置**（编码前、写帧到推流前）注入**源端时间**（建议用 NTP 同步后的系统时间或 PTP，便于与 C2 对齐）。

**注意**：比较「画面时间」与「C2 显示该帧的当前时间」时，**AGX 与 C2 的时钟需同步**（如 NTP），否则时间差会包含时钟偏差。

### 4.2 视频流延迟的可视化/测量工具（可选）


| 用途              | 工具/方法                                                  | 说明                                                                                                          |
| --------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **端到端（你当前方法）**  | 时间戳叠加 + 人工/录屏                                          | 在画面叠源端时间，C2 侧用当前时间相减；可录屏后逐帧看时间差，或简单脚本解析 OSD 时间                                                              |
| **端到端（更精确）**    | 高精度时钟 + 时间叠加                                           | 若需更高精度，可在帧上叠「毫秒级时间戳」或参考 stb-tester 等方案在帧内编码时间，再在接收端解析比较                                                     |
| **协议/网络层**      | [WINK RTSP Stats](https://www.wink.co/wink-rtsp-stats) | 分析 RTP/RTSP 的抖动、丢包、码率等，不直接给出「画面到眼」的延迟，但可排查网络导致的额外延迟                                                         |
| **Pipeline 内部** | GStreamer 等                                            | 本仓库用 Gst 解码/编码；若需看「解码→编码」各环节耗时，可在 pipeline 各 element 打 `GstClock` 或自定义 probe 统计间隔，用于支撑 SSF-003，而不是直接测 C2 拉流 |
| **专业视频延迟**      | stb-tester latency-clock、video-latency-toolkit 等       | 通过生成带时间信息的测试视频或在输出端打时间戳，做采集端与显示端时间差测量，适合实验室环境                                                               |


**实际建议**：  

- **SSF-007 以「时间叠加 + 时间差」为主**即可：在 AGX 推流前叠源端时间（复用或参考 `videoRtspMtxTest.cpp`），C2 拉流后用人眼或录屏看「当前时间 − 画面时间」。  
- 若需要**可视化曲线/报表**：可把每次测量的「画面时间」与「C2 当前时间」记下来，用 Excel/脚本画「延迟随时间」曲线或直方图。  
- 若后续要区分「网络/缓冲」与「编码/解码」，再考虑 WINK 或 GStreamer 做分段分析。

## 5. 小结

- **SSF-003**：嵌入式测「解码→共享内存→给 AI 前」；AI 测「拿到帧→算法完成」；两者相加与 10ms 对比；现有 AI 侧已有 timestamp 与 delay 显示可复用。  
- **SSF-005**：以多次「点击播放→首帧出现」测试取平均/百分位为主；若有 C2 首帧回调可做自动化；200ms 为规范，可额外统计 1s 内出画比例。  
- **SSF-007**：在视频中叠加源端时间、对比 C2 拉流看到的时间差是通用做法；仓库内 `videoRtspMtxTest.cpp` 已有时间叠加示例，可接到实际推 mediaMTX 的路径并保证 AGX/C2 时钟同步；需要「可视化」时可对多次测量结果做曲线或直方图，必要时再配合协议层/专业延迟工具做细分分析。
