# 活设计文档驱动开发（Living Design Doc）

> 提炼自 Spotter AGX 时间同步（`time_sync`）系列文档实践。  
> **不是**「用哪个 AI 产品」的说明书，而是：**人机协作做复杂特性时，用文档把决策、边界、演进锁死**，避免 AI 漂移与口头知识丢失。

## 何时启用

- 跨模块（协议 / 驱动 / boot / 业务 / 云端）的系统特性
- 需求会随现场标定、硬件接线、产品优先级反复修正
- 需要后人（或下一轮 AI 会话）快速接上上下文

## 何时不用

- 单文件小修、纯重构、无产品语义变更
- 已有稳定详设且本次只改实现细节（改完同步一小节即可）

---

## 一、文档分层（必遵守）

做复杂特性时，至少拆成 **两层**（第三层按需）：

| 层 | 读者 | 写什么 | 不写什么 |
|----|------|--------|----------|
| **产品 / 系统需求** | 产品、系统、联调 | 精度指标、模式语义、协议字段、P0 原则、硬件接口约定 | 函数名、类图细节、每次 API 瘦身 |
| **软件详设** | 实现者 / AI | 架构、时序、模板/配置规则、模块职责、文件清单、与代码对齐的版本记录 | 营销式概述 |
| **模块专篇**（可选） | 模块 owner | 单模块数据流、API、过滤规则、设计决策表 | 重复抄产品全文 |

**对齐规则**：产品改语义 → 先改产品文档版本行 → 再改详设「变更亮点」→ 再改代码。禁止只改代码不留版本说明。

**time_sync 对照**：

- 产品：`Spotter系统时间同步设计-V3.1.md`
- 详设：`time_sync_design-V3.3.md`
- 专篇：`gnss_time_feeder详细设计方案.md`

## 二、版本履历 = 决策账本（核心）

每次有意义的变更，在详设顶部 **版本记录表** 追加一行：

```markdown
| 版本 | 日期 | 作者 | 变更说明 |
|------|------|------|----------|
| vX.Y.Z | YYYY-MM-DD | 人名 | **一句话主题**：① … ② …；影响文件/协议；关联 §章节 |
```

**好的变更说明**：

- 写 **为什么 / 相对上一版改了什么**（旧→新对照）
- 点名协议字节、设备路径、删除的 API、废除的需求条款
- 大版本后跟 **「变更亮点」对照表**（主题 | 旧 | 新）

**坏的变更说明**：

- 「优化代码」「更新文档」
- 只列文件名不说语义

小步迭代节奏（可借鉴 time_sync）：

1. 对齐上游产品 / 协议
2. 架构拆模块（职责边界写清）
3. 现场/硬件事实纠偏（如 pps0=ktimer vs pps1=gpio）
4. boot / 权限 / 启动顺序类系统问题
5. 性能与切源加速
6. API 收敛与旁路清理
7. 遗留问题显式挂账（P2 暂不修也要写清）

---

## 三、每轮交付物清单（AI 会话结束前自检）

做完一轮功能或修完一类问题，至少留下：

- [ ] 版本号 bump + 版本表一行
- [ ] （可选）变更亮点表：旧行为 vs 新行为
- [ ] **职责 / 非职责**（本模块做什么、明确不做什么）
- [ ] 关键数据流或时序（ASCII / Mermaid 均可）
- [ ] 涉及的 **文件清单**（增/改/删）
- [ ] 若删旁路或旧 API：**收敛清单**（已删项 + 替代入口）
- [ ] 若暂不修：**遗留问题**节（现象、根因、影响、优先级、跟踪条件）
- [ ] 设计与代码不一致时：在文档写 **实现注记**（「设计意图 vs 当前实现」），禁止 silently 漂移

## 四、设计写作模板（复制即用）

### 4.1 模块专篇骨架

```markdown
# <模块名> 详细设计

> 版本 / 源文件 / 作者 / 日期 / 关联详设章节

## 1. 模块定位
（一句话 + 上下文图）

### 1.1 核心职责（表格）
### 1.2 非职责（明确边界）

## 2. 系统上下文
### 2.1 端到端数据流
### 2.2 接入层原则（如：只做透传）
### 2.3 与上下游集成

## 3. 内部架构 / API
## 4. 关键判定与状态机
## 5. 设计决策摘要（决策 | 方案 | 理由）
## 6. 建议单测覆盖项
## 7. 调用关系
```

### 4.2 变更亮点表

```markdown
| 主题 | 上一版 | 本版 |
|------|--------|------|
| … | … | … |
```

### 4.3 遗留问题节

```markdown
## N. 遗留问题：<标题>（P2）
> 状态：暂不修复  
> 优先级：P2  
> 现象 / 根因 / 影响面 / 为何暂不修 / 何时再打开
```

### 4.4 代码收敛清单

```markdown
## 代码收敛清单（日期）
### 最终对外 API
### 已删除 API / 类型 / 脚本 / 旁路
### 替代入口（唯一真相源）
### 单测 / 文件清单同步情况
```

## 五、工程原则（从 time_sync 踩坑提炼）

1. **单一真相源**：控制面/设钟/状态推断收敛到一个 mgr；旁路（脚本、云端、旧 opcode）要么删要么显式挂到同一入口。
2. **职责解耦**：数据面常开、选源由配置决定（例：feeder 恒写 SHM，chrony 模板决定是否读）。
3. **硬件事实写进文档**：设备节点名、GPIO、delay/offset 标定值、禁止误用的假源（如 ktimer）。
4. **启动顺序是需求**：boot 调序、`--no-start`、谁先创建 SHM，必须进详设，不能只活在脚本注释里。
5. **P0 原则显式化**：如「重启后时间正确优先」；与之冲突的旧需求用「废除项」表划掉。
6. **实现与设计双轨标注**：未落地的设计意图标「尚未落地」；已删又恢复的路径写演进史，避免后人按旧节实现。
7. **小步可回放**：一天可以多个 patch 版（v3.3.5…），但每步主题单一，便于 cherry-pick / 复盘。

## 六、人机协作用法（无绑定具体 AI 产品）

文档 **不会**规定必须用 Cursor / Claude / 某 skill。可复用的协作方式是：

| 角色 | 做法 |
|------|------|
| 人 | 定 P0、验收标准、现场现象、协议权威来源 |
| AI | 按「产品→详设→代码→回写版本行」执行；改前读关联 §；改后更新亮点表与文件清单 |
| 会话交接 | 新会话先读最新版本记录 + 变更亮点，再动代码 |
| 防漂移 | 任何「文档写 A、代码做 B」必须写实现注记或改文档 |

**提示词片段（可贴进任务描述）**：

```text
先读产品文档相关条款与详设最新版本记录；
实现须与详设一致；若发现文档过时，先提差异再改；
完成后：bump 文档小版本、写变更说明（旧→新）、更新文件清单；
暂不修的问题写入遗留问题节（P2），不要默默留下行为坑。
```

## 七、与仓库已有规范的关系

- C++ 写法：遵循 `agx-cpp-engineering`
- 提交信息：遵循 `commit-cn`
- Bug 根因：可叠加 `five-cn` / `bug-fix-cn`
- 本 skill 管的是 **复杂特性的文档与演进纪律**，不替代编码规范

## 八、反模式

| 反模式 | 后果 |
|--------|------|
| 只维护一份 3000 行「大一统」且无版本表 | 无法回放决策，AI 易按过时节实现 |
| 产品与实现混写 | 评审对不齐，协议字节和函数实现搅在一起 |
| 删除旁路不写收敛清单 | 半年后「谁还在 set_time.sh」无人知 |
| 现场标定值只在聊天记录 | 换人/换会话必丢 `delay`/`offset` |
| 文档宣称已实现、代码未落地且不标注 | 联调按假能力验收 |
| 一轮改协议+重构 API+清旁路+改 boot | 无法定位回归 |

## 九、最小落地检查（PR / 合入前）

- [ ] 产品语义变更是否有产品文档版本行？
- [ ] 详设是否有对应版本 + 亮点或 § 更新？
- [ ] 模块边界（职责/非职责）是否仍成立？
- [ ] 启动顺序 / 硬件路径 / 协议长度是否与实现一致？
- [ ] 遗留问题是否显式挂账而非口头「以后再说」？
