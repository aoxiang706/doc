# 和普 PTZ 冷启动视频延迟 — 汇报摘要

> **日期**：2026-06-26  
> **设备**：SSF200（Spotter）+ 和普 PTZ + AGX  
> **验证环境**：实验室（AGX `192.168.2.132` + 和普 PTZ，同步断电观测）

---

## 一、问题是什么

现场反馈：设备上电后，**约 1–2 分钟**才在天盾、C2 上看到视频，体验较差。

初步分析结论：**AGX 侧推流编码本身不慢**（视频源就绪后约 1 秒可出画）。总耗时主要由 **和普 PTZ 首帧解码等待（20～51 秒）与内置 RTSP 流媒体服务器冷启动**、**AGX 系统与服务启动**、**现场供电环境** 等因素叠加，需分开看待、分开推进。

---

## 二、初步分析工作

在实验室对冷启动链路做了日志采集与上电观测，主要包括：冷启动时间戳记录、启动脚本与 monit 机制梳理、链路耗时拆解（含**首帧解码等待**）、责任归属梳理。

**测量方式**：AGX 与 PTZ 同时断电再上电，以系统日志统计各环节时间点（T0 = AGX 上电）；**首帧解码等待** = `ptz_service` 启动 → 首帧 `Decoder FPS`（属和普设备侧，见 §3.2）。

---

## 三、分析结论

### 3.1 责任边界

| 归属 | 现象 | 责任方 |
|------|------|--------|
| **和普 PTZ** | 见 3.2（首帧解码等待、RTSP 流媒体服务器冷启动等） | **和普供应商** |
| **AGX 内部** | 视频服务启动偏晚等 | **我方** |
| **现场环境** | 频繁断电加剧冷启动 | **现场工程** |

### 3.2 和普 PTZ（设备侧，单独列出）

以下均属**和普供应商**问题，**AGX 软件无法替代**：

| 问题项 | 现象 | 说明 |
|--------|------|------|
| **首帧解码等待** | `ptz_service` 已启动后，仍须等待 **20～51 秒** 才能拉到首帧 | 日志中的「PTZ 等待」即此项（`ptz_service` 启动 → 首帧 `Decoder FPS`），**不属于 AGX 侧耗时** |
| **内置 RTSP 流媒体服务器** | 上电后 RTSP 服务可用、可拉流时间**偏长且不稳定** | 和普 PTZ 自带 RTSP 服务（`:554`）；首帧解码仍须 **~51s**，说明 **`ptz_service` 已在等、和普流媒体服务器迟迟不出流**，瓶颈在设备侧 |
| **云台硬件自检** | 回零、镜头初始化等 | 与 RTSP 出流叠加，导致冷启动方差大 |

> **需找和普供应商**：推动缩短自检 + RTSP 流媒体服务冷启动时间，降低首帧解码等待方差。

### 3.3 AGX 内部（出厂配置）

- `ptz_service` **未进**开机脚本，多靠 **monit** 拉起，常推迟到上电后约 **60 秒**。
- 单独调整 MediaMTX 启动先后（初步各 2 轮、monit 不变）**未见稳定收益**；关键在 **`ptz_service` 是否随系统主动拉起**。

### 3.4 现场环境

建议加 UPS / 稳压，减少频繁断电。

---

## 四、实验室对比（各 2 轮，初步）

| 对比项 | 未做任何修改（出厂 boot） | 两项 boot 顺序调整（初步 2 轮） |
|--------|---------------------------|----------------------------------|
| **配置** | MediaMTX 脚本末尾；`ptz_service` 由 monit 拉起 | MediaMTX 提前；`ptz_service` 进 `auto_boot`、在 `ptz100_ai` 前 |
| **`ptz_service` 启动** | **~+62s** | **~+20s** |
| **本地视频就绪** | **~82s**（72s / 92s，波动大） | **~71.5s**（71s / 72s，较稳） |
| **首帧解码等待（和普）*** | ~17s（monit 晚起，**不可代表真实等待**） | **~51s**（**20～51s** 量级） |

\* **首帧解码等待** = `ptz_service` 启动 → 首帧 `Decoder FPS`；属**和普 PTZ 设备侧**指标（云台自检 + 内置 RTSP 流媒体服务器 `:554` 就绪），**非 AGX 拉流/解码性能问题**。出厂 monit 晚起时日志值偏小，以 boot 调整轮 **~51s** 为准。

**对比结论**

1. **出厂配置**：`ptz_service` 启动晚（monit ~+60s），出画 **~82s** 且波动大。  
2. **两项 boot 调整**：`ptz_service` **提前约 40s**（~+20s），出画 **~71.5s**、两轮一致；**方向初步有效，待多轮统计**。  
3. **和普设备仍是主瓶颈**：首帧解码等待 **~51s**（**20～51s** 量级），说明和普 **RTSP 流媒体服务器冷启动后可拉流时间偏长**；总出画不能单靠 AGX boot 优化解决。

| 优先级 | 方向 | 说明 |
|--------|------|------|
| **P0** | 和普供应商反馈 | 首帧解码等待 **20～51 秒**、RTSP 流媒体服务器冷启动慢、方差大 |

## 八、结论

### 8.1 和普 PTZ（设备侧）

**首帧解码等待 20～51 秒**、内置 **RTSP 流媒体服务器（`:554`）冷启动后可拉流时间偏长**，属设备侧问题，**需找和普供应商**推动优化；AGX 软件无法替代。

### 8.2 AGX 内部（暂不考虑和普设备侧）

以下仅看 **AGX 侧可控环节**（本地视频就绪 = `ptz_service` 启动 + 首帧解码 + 编码推流；首帧解码仍依赖和普，但可对比 **AGX 服务启动早晚** 对总出画的影响）：

| 场景 | boot 配置 | `ptz_service` 启动 | 本地视频就绪 | 说明 |
|------|-----------|-------------------|--------------|------|
| **出厂（未改）** | MediaMTX 脚本末尾；`ptz_service` 由 monit 拉起 | **~+62s** | **~82s**（72 / 92，波动大） | monit 排队是 AGX 主因 |
| **修改一：MediaMTX 提前** | 仅调整 MediaMTX 启动先后，monit 不变 | 仍 ~+60s | **未见稳定缩短** | 初步各 2 轮，**单独无效** |
| **修改二：视频链路主动拉起** | MediaMTX 提前 + `ptz_service` 进 `auto_boot`、在 `ptz100_ai` 前 + `nexus_gateway` 紧随 `ptz100_ai` | **~+20s** | **~71.5s**（71 / 72，较稳） | 两项配合，**初步各 2 轮有效**（云推待现场验证） |

**AGX 侧量化（初步 2 轮）**

| 指标 | 出厂 | 两项 boot 调整 | AGX 侧改善 |
|------|------|----------------|------------|
| `ptz_service` 启动 | ~+62s | ~+20s | **约 −40s** |
| 本地视频就绪 | ~82s | ~71.5s | **约 −10s**（当轮和普首帧解码仍 ~51s） |

> 下午追加多轮验证：和普首帧解码较快（~12s）时，本地出画可进一步至 **~32s**；和普偏慢（~51s）时仍约 **~71s** 量级——**总出画下限仍取决于和普**。

**AGX 优化方案（建议，待多轮验证后合入）**

1. **MediaMTX 提前启动**：在 `auto_boot_app.sh` 中，于所有视频相关 ROS 节点之前启动。  
2. **`ptz_service` 纳入开机脚本**：排在 `ptz100_ai` 之前（先拉 PTZ RTSP 写 SHM，AI 再读处理）；**避免仅依赖 monit 排队拉起**。  
3. **`nexus_gateway` 从脚本末尾提前至 `ptz100_ai` 之后**：负责天盾 MQTT 注册 + 从本地 MediaMTX 拉 RTSP 云推；**不必放在 AI 之前**（须等编码推流就绪才有流可拉），但应尽早启动以便注册/推流准备与和普首帧解码等待**并行**；实验室暂无法验证天盾云推（MQTT 不可达），**待现场复测**。  
4. **目标顺序**：`mediamtx` → `ptz100_ros` → `ptz_service` → `ptz100_ai` → `nexus_gateway` → …  
5. **预期**：`ptz_service` 由上电后 ~60s 提前至 ~20s；在和普首帧解码正常时，本地出画有望由 ~70s 量级明显缩短（下午初步验证 ~32s，**待多轮统计**）；天盾云推收益**待现场验证**。

### 8.3 整体

要改善现场 1～2 分钟体验，需 **和普首帧解码 / RTSP 流媒体服务器改进 + AGX boot 方案验证合入 + 现场 UPS** 协同推进；当前输出为**初步分析**，量化结论待实验补充。
